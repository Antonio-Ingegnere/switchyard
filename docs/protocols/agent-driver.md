# Agent Driver Contract

## Principle

An agent driver is a protocol adapter.

It must not become a second workflow engine.

## Current implemented invocation boundary (RUNTIME-007)

All concrete executors use `run(InvocationRequest) -> InvocationResponse`.
Request contains the immutable task-only WorkUnit plus optional DiagnosticInput;
response contains outcome-only ExecutorResult plus optional bounded DiagnosticPayload.
Runtime alone assigns DiagnosticOrigin and selects transitions. See
[the RUNTIME-007 contract](../plans/runtime-007.yaml) for admission, byte limits,
and handoff semantics. Command/Codex/Claude currently reject diagnostic input;
only fake consumers exercise that capability. The interface below is historical
conceptual direction, not an implemented AgentDriver hierarchy or requirement.

## Conceptual interface

```ts
interface AgentDriver {
  capabilities(): AgentCapabilities;

  run(request: AgentRequest): Promise<AgentResult>;

  resume?(
    session: AgentSession,
    request: AgentRequest
  ): Promise<AgentResult>;

  cancel?(runId: string): Promise<void>;
}
```

The TypeScript notation above and below is illustrative, not a language decision. Python is the current baseline because the existing prototype uses Python; the implementation language remains a separate architectural decision.

## Normalized request

Conceptually:

```ts
interface AgentRequest {
  task: string;
  cwd: string;

  mode?: "plan" | "implement" | "review";

  context?: ContextRef[];

  limits?: {
    timeoutMs?: number;
    maxTurns?: number;
  };

  tools?: ToolPolicy;
}
```

## Normalized result

Conceptually:

```ts
interface AgentResult {
  status:
    | "success"
    | "failed"
    | "error"
    | "timeout"
    | "cancelled";

  output: string;

  session?: {
    provider: string;
    id: string;
  };

  usage?: {
    inputTokens?: number;
    outputTokens?: number;
    costUsd?: number;
  };

  events?: AgentEvent[];
}
```

## Capabilities

Do not force every provider into a false lowest-common-denominator abstraction.

Capabilities may include:

```text
sessions
structured_output
streaming
max_turns
tool_control
usage_reporting
native_sandbox
```

The runtime may adapt policy based on capabilities.

## Hard rule

A driver may report:

```text
success
failed
error
timeout
cancelled
usage
session
events
```

The result contract must not contain:

```text
next_state
```

## Initial drivers

Likely first adapters:

- Codex;
- Claude Code.

Keep both behind the same core contract.

Provider-specific session handling, CLI parsing, SDK events, and usage fields remain inside each adapter.

Concrete technical adapters retain the vocabulary `success | failed | error | timeout | cancelled`.
Since RUNTIME-V2-A, direct runtime flows may declare arbitrary semantic outcomes in
`State.on`. The runtime accepts a result only if it is an exact nonempty string
without NUL, is not reserved, and appears in the current state's transition map.
There is no trimming, coercion, normalization or global registration. The reserved
executor-outcome set is exactly `{budget_exceeded}`: it is generated by the runtime,
not returned by a driver. Other runtime event kind names are not transition triggers
unless a flow independently declares them as semantic strings.

`error`, `timeout` and `cancelled` are executor-returned outcomes, not synthesized by
runtime. Command spawn errors and timeouts are normalized by the command adapter;
Codex/Claude normalize command failure to error. Cancellation remains an allowed
technical result without a cancellation mechanism added here. Escaped exceptions
continue to abort with ExecutionError/run_error instead of becoming an error result.

Undeclared outcomes fail immediately with ExecutionError identifying the current
state, returned value and declared semantic outcomes. Like malformed responses, they
emit invocation-scoped run_error with no outcome before invocation_finished. No
transition or retry occurs. Valid outcomes are recorded unchanged. Event fields and
JsonlRecorder are unchanged; the historical reader now validates outcome strings
lexically and excludes reserved control-plane values instead of using the old
technical whitelist. It cannot check state membership without the original flow.
Old missing-transition histories containing invocation_finished followed by
run_error-with-outcome remain readable.

FLOW-001 YAML retains its existing technical-outcome vocabulary; this runtime
capability does not expand that version's loader. OUTCOMES remains exported as a
legacy adapter vocabulary constant, not a runtime validation rule. `timeout` denotes an invocation missing its deadline. Each invocation receives an explicit immutable Work Unit payload, including before a full Context Engine exists; provider session history is never implicitly required context.

## Escaped exceptions

Per [ADR-007](../decisions/007-executor-contract-exceptions.md), expected operational failures must be normalized into ExecutorResult. Exceptions escaping the executor boundary abort the run through ExecutionError; they are not converted to `error`, routed through normal transitions, or automatically retried.
